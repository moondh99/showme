# R01·R03·R08 수정·검증 결과

2026년 11월 2일. [수정 전 재평가](POSTFIX_REAUDIT.md)의 세 항목을 수정했다. 알려진 AI 연출 사진과 별도 수동 승인 검증 안내서를 사용했다. 실제 현장 자료·사람 평가는 아니다.

## 변경과 판정

| 항목 | 변경 | 검증 |
|---|---|---|
| R01 | 대상 설명의 색 단어 대신 명확한 시각 질문을 사진 경로로 처리. 나머지는 승인 규칙 경로를 기본으로 사용 | 자연어 16개 분류 회귀. 실제 일반 입력 ‘파란색 펜은 운영자 메모 전용인가요?’와 ‘파란색 펜의 역할이 뭔가요?’ 모두 procedure/answered |
| R03 | 관련 문장 발췌와 함께 instruction·completion_check 전체를 서버가 `approved_context`로 응답·저장. 화면은 항상 펼쳐진 문맥을 표시 | 첫 문장만 인용하는 통제된 검사에서도 뒤 금지와 다른 필드의 완료 조건 보존. 실제 API·Chrome에서 금지 문장·완료 조건 표시 |
| R08 | `recheck_of`로 거절과 성공 연결. 범위를 검증하고 답변 저장과 해당 보완 질문 해결을 원자적으로 처리 | 실제 거절 → 연결된 승인 규칙 답변 → 담당자 목록 11→10. 정확히 그 질문만 제거되고 다른 항목은 보존 |

R03은 모든 금지 표현을 감지하는 정규식을 만드는 방식으로 해결하지 않았다. 관련 답변은 짧게 유지하되, 두 승인 필드의 전체 문맥을 응답과 화면에서 반드시 동반한다. `answer` 문자열 하나만 떼면 완전한 지시가 아닐 수 있다. 일반 문맥 전체를 함께 읽는 비용이 생기며, 모델이 대상과 인용을 잘 연결했는지는 별도 의미 검증 문제다.

## 회귀 검사

Python **73개**, JavaScript **5개**, 합계 **78개** 통과. JavaScript 구문 검사와 변경 공백 검사 통과.

새 검사 9개는 다음을 포함한다.

- 자연스러운 역할·전용·대상·시점 질문과 명확한 시각 질문 구별.
- 모델이 짧게 인용해도 두 승인 필드 전체를 API에서 제공.
- 같은 질문의 재확인 성공으로 원래 항목만 해결. 재시작·대화 정리 후에도 해결 근거 보존.
- 재확인 실패 때 원래 항목 유지, 중복 보완 방지, 제공자 오류 뒤 재시도 가능.
- 다른 승인본·단계·질문·선택, 이미 답한 질문, 만료된 기록으로 잘못 해결하지 못함. 유료 모델 호출 전에 거부.
- 재확인 중 대상 확인 대화가 필요하면 최종 승인 답변까지 연결 상속.
- 사진 답변·거절에는 승인 문맥을 잘못 붙이지 않음.

## 실제 호출 및 브라우저

호출 전 계획: `state/evidence/recovery-fixes-plan.json`. 총 실제 Muse 호출 **10회**이며, 최종 제품 시나리오 6회 외에 초기 형식 오류 3회와 직접 진단 성공 1회가 포함된다. 신규 SAM 호출 없이 기존 실제 SAM 선택을 재사용했다. 실패를 성공 수치에 포함하지 않는다.

초기 2개 제품 요청은 ‘AI 응답 형식을 확인하지 못했습니다’로 안전하게 거절됐다. 첫 진단에서도 모델 검증 오류가 관측됐으나 진단 기록 직렬화가 실패해 상세 오류를 저장하지 못했다. 두 번째 진단은 성공했다. 제공자 원문·키는 로그에 남기지 않았다. procedure 응답에서 위치 강조를 비우고 승인 근거를 인용하도록 프롬프트도 명확히 했다. 초기 오류의 정확한 세부 원인을 확보하지 못했으므로 이 변경이 모든 형식 오류를 없앴다고 주장하지 않는다. 최종 6회는 모두 기대 결과를 보였으며 일반적인 성공률 추정 자료가 아니다.

| 최종 사례 | 경로 | 실제 결과 |
|---|---|---|
| 메모 전용인가요? | 일반 입력 → 실제 API → Chrome | 파란 펜의 승인 용도. 재확인 버튼 없이 정답 |
| 역할이 뭔가요? | 실제 제품 API | 파란 펜의 승인 용도 |
| 선택한 물체는 무엇에 쓰나요? | 기존 검은 펜 SAM 선택 → 실제 제품 API | 참가자 서명에는 검은 펜 사용 |
| 금지·완료 조건 | 별도 수동 승인 안내서 → 일반 입력 → 실제 API → Chrome | ‘참가자에게 건네지 않습니다’와 ‘잉크가 마른 뒤 접수를 시작합니다’를 접지 않고 표시 |
| 예전 명시적 사진 목적 | 실제 제품 API, ‘파란색 펜은 운영자 거예요?’ / appearance | 사진에서 용도를 추론하지 않고 insufficient_information, 미처리 보완 생성 |
| 연결된 승인 규칙 재확인 | 같은 질문 / procedure + recheck_of → 실제 API → 담당자 Chrome 새로 확인 | answered, recovered_gap_id 일치. 보완 11→10, 정확히 원래 질문만 해결 |

R08의 실제 연결 요청은 HTTP로 전송했고 담당자 목록 변화를 브라우저에서 확인했다. 별도 임시 저장소와 통제된 응답 재생 환경에서도 학습 화면의 재확인 버튼을 직접 클릭했다. 화면의 해결 안내와 원래 질문 id 전달, 실제 저장소의 해결 기록을 확인했다. 이 버튼 검사는 모델 답변의 의미를 평가하지 않으며 새로운 Meta 호출도 아니다. 연속 확인 대화·실패 경계는 회귀 검사로 확인했다.

기존 승인본 **3개 해시 동일**. 새 조건 검증용 승인본 1개만 별도로 추가했다. 원래 펜 규칙과 공개 데모 승인본을 바꾸지 않았다.

Chrome 크기 재정의를 시도했으나 실제 측정은 데스크톱 너비로 유지됐다. 재정의를 해제했으며 이번 결과를 신규 390px 모바일 검사 통과로 기록하지 않는다. 실제 휴대전화 검증도 수행하지 않았다.

## 보완 목록 보존 규칙

재확인 성공은 procedure/answered이고 인용 검증을 통과해야 한다. 모델 오류·정보 부족·사진 관찰 답변만으로는 원래 질문을 해결하지 않는다. 답변과 해결 시각을 learning_gaps에 남겨 대화의 24시간 정리와 분리한다. 동일 질문의 실패한 재확인으로 새 미처리 항목을 중복 생성하지 않는다. 기존 담당자가 완료한 상태를 자동 답변이 덮어쓰지 않는다.

과거 기록에서 질문 문장이 같다는 이유만으로 성공과 거절을 추측해 일괄 연결하지 않는다. 이전 재평가의 연결 없는 성공과 거절은 기존 상태를 유지한다. 모델 답변에 근거가 있다는 판정은 사람의 의미 정확성 확인과 동일하지 않다.
