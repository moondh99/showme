# ShowMe 핵심 기능 구현 계획

[제품 기획](PRODUCT_SPEC.md)을 구현 가능한 작업과 계약으로 나눕니다. 2026년 11월 1일 작업 1~3을 구현했습니다. 단일 단계 흐름의 [첫 구현](FIRST_SLICE_RESULTS.md)에 이어 최대 6단계 입력·순서 편집·단계별 검토·전체 승인·학습 진행을 실제 API와 브라우저에서 확인했습니다. 현재 구현 범위는 [다단계 검증 결과](MULTISTEP_RESULTS.md)를 참고하세요. 작업 4의 현재 단계 질의응답·확인 대화·근거 표시도 [구현·검증](QUESTIONS_RESULTS.md)했습니다. 후속 배포·현장 사용자 검증은 남아 있습니다.

## 구현 방향

첫 구현은 **FastAPI 웹 서버, 같은 서버의 HTML/CSS/JavaScript 화면, SQLite와 로컬 사진 파일 저장**으로 확정했습니다. 검증한 이미지 처리·Meta 요청·응답 검사 로직을 재사용하고 저장까지 한 흐름으로 검증했습니다. 현재 서버는 loopback에서만 실행하며 외부 호스트와 공개 배포는 다음 작업입니다.

학습 링크를 다른 기기에서 열려면 서버의 영속 저장이 필요합니다. 배포는 사진 디렉터리와 SQLite 파일이 유지되는 단일 서버를 전제로 합니다. 파일을 보존하지 않는 실행 환경으로 배포할 경우 저장 방식을 바꾸는 작업이 선행돼야 합니다. 호스팅 계정이나 배포 대상은 아직 선택하지 않았습니다.

작성자는 한 명으로 시작하고 작성 화면·변경 요청은 작성자 세션으로 제한합니다. 초기 작성자 접근은 배포 시 설정한 단일 비밀번호로 서버 세션을 발급하는 최소 방식으로 계획합니다. 학습 링크는 승인본 읽기와 해당 승인본 질문만 허용합니다. 다중 계정·조직 관리는 만들지 않습니다.

## Module과 Interface

Module의 Interface에 입력·상태 제약·실패·저장 조건을 함께 모읍니다. 추상화 계층을 늘리기보다 다음 세 Module에 책임을 모읍니다.

| Module | 작은 Interface | 내부에서 처리할 내용 |
| --- | --- | --- |
| Media | `registerPhoto(file)`, `readPhoto(photoId, access)` | 형식·크기 검사, EXIF 회전·메타데이터 제거, 리사이즈, 이미지 해시·크기 저장, 파일 접근 권한 |
| Guides | `saveDraft(command)`, `getDraft(id)`, `publish(id, draftVersion)`, `readPublished(shareId)` | 입력·순서·검토 상태 검사, SQLite 저장, 승인본 고정, 접근 권한, 갱신 충돌 |
| Vision | `generateStep(photoId, note, goal)`, `answerStep(revisionId, stepId, question, clarification)` | 허용 사진·승인 내용 조회, Meta 요청, 구조·근거 ID·좌표 검사, 작업 상태와 오류 |

Meta 호출을 대체할 수 있는 Seam은 Vision 내부의 실제 외부 요청 지점에 둡니다. 제품 로직 테스트는 위 Interface를 통해 관찰하고, 외부 응답을 고정할 때만 테스트용 Adapter를 사용합니다. 저장소 종류를 가정한 범용 프레임워크는 만들지 않습니다.

기존 `scripts/meta_vision.py`는 검증 진입점으로 유지합니다. 재사용할 전처리·응답 검사 코드는 `src/showme/`로 옮기고 검증 도구와 앱이 같은 Implementation을 호출하도록 합니다. 이전 실험 기록과 질문 세트는 보존합니다.

## 저장할 데이터

| 대상 | 주요 필드 | 불변 조건 |
| --- | --- | --- |
| Photo | id, 저장 경로, width, height, sha256, 출처, 생성 시각 | 회전·리사이즈 후 동일 사진을 표시와 모델 입력에 사용, 교체는 새 ID |
| GuideDraft | id, title, goal, version, orderedSteps, updatedAt | 명시적 저장, version 충돌은 기존 초안을 덮어쓰지 않음 |
| DraftStep | id, photoId, operatorNote, title, instruction, completionCheck, highlights, reviewed | 고유 ID로 사진과 내용 연결, 배열 순서가 작업 순서, 내용·위치 변경 시 검토 해제 |
| Highlight | id, label, box, origin | 0~1000 정규화 좌표, 양의 넓이·높이, origin은 model/author |
| GuideRevision | id, guideId, revisionNumber, immutableSteps, shareId, approvedAt | 승인 순간 복사, 원래 초안 갱신과 분리 |
| LearningProgress | revisionId, completedStepIds | 브라우저 저장, 승인본별 구분, 다른 기기 동기화는 범위 밖 |
| QuestionTurn | revisionId, stepId, question, clarification, answer, evidenceRefs, status | 현재 승인본·단계만 참조, 질문이 본문을 수정하지 않음 |

파일 업로드의 제품 제한은 JPEG/PNG/WebP, 파일당 10MB, 안내서당 최대 6장으로 시작합니다. 이는 앱의 제한이며 Meta API 최대 한도가 아닙니다. 긴 변 1600px 전처리와 좌표 기준은 검증 도구를 재사용합니다.

사진 위 좌표는 이미지 자체의 표시 영역을 기준으로 변환합니다. 여백이 있는 화면 컨테이너 전체를 좌표 기준으로 삼지 않습니다. 파일 내용 검사와 디코딩이 끝나기 전에는 표시·Meta 전송을 하지 않습니다.

## HTTP 계약 초안

사진·초안·승인본 변경 요청은 작성자 세션이 필요합니다. 학습 링크 요청은 해당 승인본 범위만 접근합니다. 경로와 형식은 첫 구현에서 고정합니다.

| 요청 | 입력·출력 | 오류와 제약 |
| --- | --- | --- |
| `POST /api/photos` | multipart 사진 → photoId, canonical URL, 크기 | 형식·크기 오류, 작성자만 업로드 |
| `POST /api/guides` | 제목·목표 → draftId, version | 빈 제목·잘못된 입력 거절 |
| `PUT /api/guides/:id` | version과 전체 초안 → 새 version | 저장 실패 시 기존 데이터 유지, 오래된 version은 409 |
| `POST /api/guides/:id/steps/:stepId/generate` | 저장된 사진·메모·목표 → 단계 초안과 입력 version | 입력이 바뀐 동안 도착한 결과는 최신 초안을 덮어쓰지 않음 |
| `POST /api/guides/:id/publish` | 검토한 draftVersion → revisionId, shareUrl | 미검토·필수 필드 누락·version 충돌은 승인 거절 |
| `GET /api/learn/:shareId` | 승인본 → 읽기 전용 단계·사진 | 초안과 다른 승인본의 자료는 반환하지 않음 |
| `POST /api/learn/:shareId/questions` | step_id, question, 선택적 clarification_of·selection_id → 답변·근거·상태 | 현재 승인본의 해당 단계만 조회 |

단계 생성은 첫 버전에서 한 사진씩 처리합니다. 전체 생성 버튼을 추가하더라도 진행 상태는 완료된 단계 수로 표시하고 실패 단계만 다시 요청합니다. 전체 생성 소요 시간과 여러 사진 동시 생성은 아직 측정하지 않았습니다.

질문 결과의 제품 상태는 `answered`, `not_visible`, `needs_clarification`, `insufficient_information`입니다. 전송·형식 오류는 답변 상태와 분리합니다. `answered`는 물체 질문이면 유효한 강조 영역을 포함할 수 있고, 승인된 설명에 대한 답변이면 문장 근거만 가질 수도 있습니다.

기존 실험의 `found/not_found/needs_clarification` 구조는 물체 찾기용입니다. 앱에서는 사진 대상의 존재와 절차 정보의 존재를 분리해 새 응답 구조를 검증해야 합니다. 새 응답 구조는 [실제 질문 API 검증](QUESTIONS_RESULTS.md)에서 확인했습니다.

답변은 서버가 확인한 승인본·단계 ID에 묶이며, 근거의 `source`는 현재 사진·설명·완료 확인 중 하나입니다. 승인 문구는 해당 필드의 실제 부분 문자열인지 검사합니다. 프롬프트가 만든 문자열을 그대로 데이터 경로로 사용하지 않습니다. 입력 메모와 사진의 문구는 지시문이 아닌 자료로 전달합니다.

## 기다림·실패·접근 처리

- 단계 생성 중에는 해당 입력을 고정하거나 입력 version을 기록해 오래된 결과 적용을 막습니다.
- 질문은 현재 단계에서 한 번에 하나만 실행합니다. 다른 단계로 이동한 뒤 도착한 응답은 원래 단계에 연결해 보관하고 새 단계 위에 표시하지 않습니다.
- 사용자에게 가짜 완료 비율이나 남은 초를 보여주지 않습니다. 질문·생성 대기, 완료, 실패를 명확히 표시합니다.
- 외부 API 제한·시간 초과·잘못된 구조를 구분하고 자동 재호출은 하지 않습니다. 재시도는 사용자 행동으로 실행합니다.
- 인증 오류나 크레딧 문제의 상세 내용은 작성자에게만 보여주며 학습자에게는 일시적으로 질문을 사용할 수 없다고 안내합니다.
- 초안 생성과 학습 질의응답 모두 서버에서 Meta API를 호출합니다. 키·인증 헤더·원본 base64를 브라우저와 로그에 전달하지 않습니다.
- 공개 학습 질문은 짧은 질문 길이 제한과 서버의 동시 요청·빈도 제한을 적용합니다. 실패 시 승인된 설명 읽기는 계속 가능합니다.

## 개발 작업과 검증 기준

각 작업은 앞 작업의 완료 조건을 통과한 뒤 진행합니다. 아래 시간은 순수 개발 추정치이며 확정 일정이 아닙니다.

| 순서 | 작업 | 의존성 | 완료 증거 | 추정 |
| --- | --- | --- | --- | --- |
| 1 | 1단계 전체 흐름: 사진·메모 입력, 서버 저장, 모델 초안, 수정, 승인본 조회 | 없음 | 서버 재시작·새로고침 후 같은 승인본 조회, 실제 생성 요청 | 6시간 |
| 2 | 1~6단계 편집·강조 영역 보정·검토 상태 | 1 | 순서·사진·설명 변경 시 검토 해제, 보정한 위치 재현 | 4시간 |
| 3 | 읽기 전용 학습 링크·단계 이동·진행 복원 | 1~2 | 별도 기기에서 승인본 열기, 편집 권한 없음, 새 초안과 분리 | 3시간 |
| 4 | 현재 단계 질문·확인 대화·근거 표시·오류 처리 | 3 | 실제 물체·대상 없음·모호함·규칙 부족 질문 사례 | 4시간 |
| 5 | 승인·저장·좌표·접근 회귀 확인과 사용자 테스트 | 1~4 | 핵심 사용자 흐름 통과와 실패 사례 기록 | 3시간 |
| 6 | 영속 저장을 갖춘 배포·실제 작업 자료·데모·제출 | 5 | 배포 재시작 후 링크 유지, 실제 호출 데모, 제출 접수 | 4시간 |

합계 약 24시간으로 잡되, 실제 작업 사진 확보·사용자 모집·호스팅 접근 대기는 별도입니다. 공유 배포에 필요한 호스팅 접근과 영속 디스크 선택은 작업 1에서 확인해 작업 6의 막힘을 앞당겨 해소합니다. 사용자 모집은 구현과 별도로 조기에 준비하되 연락은 사용자 지시에 따라 진행합니다.

시간이 밀리면 전 단계 검색·사진 영역 선택 질문·SAM·다국어를 추가하지 않고, 복잡한 영역 크기 조절 대신 ‘다시 그리기’를 유지합니다. 저장·승인본 고정·근거 표시·명확하지 않을 때 확인하는 동작은 유지합니다.

## 남아 있는 검증 과제

1. 한 사진과 행동 메모로 생성한 단계가 메모에 없는 규칙을 추가하지 않는지 실제 호출로 확인합니다.
2. `insufficient_information`과 메모 근거 연결을 포함한 앱 응답 구조를 실제 모델에서 확인합니다.
3. 확인 질문 뒤 사용자의 추가 답변이 원래 질문과 연결되는지 검증합니다.
4. 공개 사진의 단일 물체 검증을 실제 작업 단계·작은 물체·가림·어두운 사진 사례로 확장합니다.
5. API 호출 성공과 앱 저장·공유·사용자 작업 성공의 완료 상태를 별도로 관리합니다.

## 질문 구현의 확정 계약

확인 대화는 서버 질문 ID로 이어가며, 클라이언트 대화 기록은 받지 않습니다. 승인본·단계별 격리와 24시간 유효 기간을 적용합니다. 화면 대화는 새로고침 시 지워지고 학습 진행은 유지됩니다. 질문 1~1,000자, 주소별 분당 10회·시간당 60회, 생성·질문 합계 동시 2개 제한을 적용했습니다. 세부 동작과 실패·수정 이력은 [질문 검증 결과](QUESTIONS_RESULTS.md)를 기준으로 합니다.

## 11월 2일 물체 선택 확정 계약

초기 P1 계획 중 사진 선택·SAM을 제품에 연결했습니다. `POST /api/learn/:shareId/selections`는 `step_id`, `point`(x/y 정수 0~1000)를 받고 선택 ID·윤곽 또는 `not_found`를 반환합니다. 서버가 승인된 사진을 읽고 원본 픽셀로 변환해 SAM 3.1을 호출합니다. 공식 파서로 스트림을 해석하고 마스크 범위·크기·누른 픽셀의 포함 여부를 검사합니다. 전체 SVG나 외부 URL 대신 제한된 SVG path만 반환합니다.

질문은 `selection_id`로 서버에 저장된 대상을 참조합니다. 승인본·단계·사진·24시간 유효 기간이 일치해야 하며 같은 선택에서만 확인 대화를 이어갈 수 있습니다. 사진의 대상은 Muse Spark가 해석하되 선택 질문의 `answered`에는 현재 승인 설명/완료 확인의 실제 인용이 반드시 있어야 합니다. 사진 근거뿐이면 서버가 정보 부족으로 유보합니다. 인용 일치 검사는 답변의 의미 전체가 정확하다는 보장은 아닙니다.

선택 기록은 별도 테이블에 저장하며 기존 질문 테이블은 선택 ID 열만 추가합니다. 승인본과 이전 질문은 보존합니다. 선택·질문은 빈도/동시 제한을 공유하고 자동 재호출하지 않습니다. [통합 검증 결과](SELECTION_RESULTS.md).


## 11월 2일 재평가 후 계약 변경

- 신규 학습 화면은 일반 질문에 `intent=auto`, 빠른 질문에 요청별 `procedure` 또는 `appearance`를 보냅니다. 누락된 값은 이전 클라이언트 호환을 위해 `procedure`입니다. 서버 응답에는 실제 처리한 `intent`가 포함됩니다.
- `auto` 확인 대화는 서버에서 부모 질문의 목적을 조회하며 승인본·단계·선택·만료 경계를 유지합니다. 일반 질문의 목적은 다음 질문으로 남기지 않습니다.
- `learning_gaps`는 대화 저장소와 분리합니다. 기존 `insufficient_information` 질문을 중복 없이 이관하고, 새 정보 부족 질문을 저장합니다. `question_turns`의 만료 정리로 이 테이블을 삭제하지 않습니다.
- 작성자 전용 `POST /api/guides/{guide_id}/learning-gaps/{gap_id}/resolve`는 엄격한 불리언 `resolved`를 받습니다. 해당 안내서의 질문만 완료/복원할 수 있고 승인본은 수정하지 않습니다. 조회는 미처리 전체를 반환합니다.
- 규칙 응답은 정확한 인용을 포함하는 온전한 승인 문장으로 구성합니다. 조건/예외·문맥 의존 표현이나 반복 인용은 보수적으로 전체 필드를 유지합니다. 사진 근거와 모델 작성 업무 답변은 규칙 응답에서 제거합니다. 전체 원문은 현재 단계의 공개 승인 필드로만 다시 표시합니다.
- [검증 결과](REAUDIT_FIXES_RESULTS.md)에 실제 호출·격리 검사·남은 의미적 한계를 구분했습니다.


## 11월 2일 재확인·승인 문맥 응답 계약

질문 API에 선택 입력 `recheck_of`를 추가했다. 원래 `insufficient_information` 질문의 id를 보내며, `clarification_of`와 함께 보낼 수 없다. 서버가 최근 24시간의 동일 승인본·단계·선택 id·질문 원문과 procedure 목적을 확인한다. 보완 목록의 임의 id를 보내는 범용 완료 API가 아니다. 확인 대화의 후속 응답은 서버에 저장된 재확인 연결을 상속한다.

응답의 `approved_context`는 procedure/answered일 때 현재 승인 단계의 instruction·completion_check 전체를 source/text 배열로 제공하며, 나머지 응답은 빈 배열이다. 모델 출력에 맡기지 않고 승인본에서 서버가 구성한다. `answer`는 관련 발췌이므로 클라이언트는 이 문맥을 함께 표시해야 한다. UI는 전체 문맥을 접지 않고 표시한다.

`recovered_gap_id`는 이번 답변이 실제로 해결한 보완 질문 id 또는 null이다. 답변 저장과 보완 질문 해결은 같은 SQLite 트랜잭션이며 `learning_gaps.recovered_by/recovery_answer/resolved_at`에 근거를 남긴다. 실패 시 기존 질문을 유지하고 재확인 거절은 중복 보완으로 만들지 않는다. 대화 만료 후에도 해결 근거는 보관된다. [검증 결과](RECOVERY_FIXES_RESULTS.md).


## 질문 모델의 전송 계약·진단 보존 보완

Pydantic의 모델 검증기는 자동 생성 JSON Schema에 포함되지 않는다. 질문 모델용 `question_response_schema(intent)`는 평범한 객체 루트 아래 `result.anyOf`로 상태별 응답을 정의하고 strict 모드를 사용한다. 답변 상태에는 목적에 맞는 근거를 필수로 하며, 비답변 상태의 근거/위치와 비확인 상태의 선택지는 금지한다. 모델 전송용 래퍼는 서버에서 제거하고 기존 GroundedAnswer 검증과 승인 인용 검증을 유지한다. oneOf/allOf와 루트 anyOf는 사용하지 않는다. [Meta 공식 제약](https://dev.meta.ai/docs/structured-output).

`VisionError.diagnostics`는 고정 원인 코드·단계·알려진 필드 경로만 포함한다. Pydantic input/ctx나 응답 원문을 로그에 직렬화하지 않는다. 질문/분할 오류 처리와 작성자 생성 오류 처리에서 안전한 진단을 model_failures에 보존한다. 재시작 후에도 최근 30일·최대 200건이 남는다.

R08의 재확인 검증은 중간 거절 기록의 recheck_of가 있으면 그 최초 id를 반환한다. 재확인을 실패한 뒤 그 실패 id로 재확인해도 원래 보완 질문을 해결한다. API 응답의 recheck_of를 통해 클라이언트가 이 연결을 유지하고 실패 카드의 재시도 제어를 표시한다.


## R10·R11 의미 판단 서비스

제품 기본 응답기는 `reasoning.answer_with_reasoning`이다. 기존 `vision.answer_question`은 비교용 단일 호출 경로로 유지한다. 새 자동 요청은 intent=auto를 서비스로 전달하고, 서비스가 확정한 resolved_intent를 저장·반환한다. 표현 규칙은 구형 명시적 사진 요청의 보호와 구형 주입 응답기의 호환 힌트로 남는다. 확인 대화는 저장된 목적을 유지한다.

PlannedAnswer는 기존 GroundedAnswer에 intent와 assessment를 더한다. assessment는 decision(policy/allowed/blocked/conditional/unknown/visual/clarify), target, conditions(source/detail/state)를 가진다. 조건은 해당 자연어 조항 전체를 단위로 하며 원자 명제의 형식 증명이 아니다. 금지 조항이 적용되는 것도 met일 수 있으므로 개별 met을 ‘행위 허용’으로 해석하지 않는다. 공개 UI는 전체 판정과 근거 조항을 구별한다.

R12 2차 이후 최초 의미 해석과 별도 전체 교정 검토에 `reasoning_effort=low`를 명시한다. 새 단순 외형은 재검토를 생략하고, 업무·선택 대상·확인 대화·미해결·업무 표현이 있는 요청은 재검토를 유지한다. 업무 표현 검사는 목적을 키워드로 확정하지 않는다. 재검토가 완전한 최종 답변을 직접 반환해 제품은 최대 2회(단순 외형/명시적 사진은 1회)다. 출력 토큰의 강제 절단·자동 재시도·실패 시 초안 반환은 없다. 사진·승인 규칙·분류/전체 교정 프롬프트·스키마·원문 및 조건 검증은 유지한다. unknown/근거 없는 allowed는 conditional, not_met은 blocked로 제한한다. 같은 모델 재검토이므로 오류 독립성을 보장하지 않는다.

공개 질문 응답은 기존 필드와 추가 assessment를 제공한다. 모델 호출 수·사용량·검토 변경 여부는 비공개 metrics에 저장한다. 질문에 제시된 상황은 가정이며 실제 신분/승인/이수 확인이나 작업 완료 판정을 대신하지 않는다. [평가 결과](R10_R11_RESULTS.md).

내부 `effort_profile=legacy`는 R12 1차의 기본 깊이+작은 검토/필요 시 세 번째 교정을 새 실제 요청으로 비교한다. `plan_low/audit_low/bounded`는 폐기 시도를 포함한 진단용 경로다. 제품 기본은 `corrective`이며 공개 요청에서 내부 정책을 선택할 수 없다. 응답 계약과 승인본은 유지하며 `audit_strategy`·`review_reason`·실제 호출별 지연과 사용량을 비공개 지표에 기록한다. [호출·지연 검증](R12_RESULTS.md).

실제 외부 요청 대기와 로컬 준비·디코딩/검증을 나눠 비공개 지표로 기록한다. 보고된 내부 추론 토큰 수는 저장하지만 내부 추론 내용은 수집하지 않는다. [긴 대기 원인과 후속 검증](R12_TAIL_RESULTS.md).
