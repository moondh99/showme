# 새 표현·조건 재평가와 API 계약 수정

2026년 11월 2일. 기준 소스 `6582ade`를 다른 질문 표현과 조건으로 평가했다. 이전 완료 판정은 좁은 재현 사례의 통과를 일반화했다. 이번에도 알려진 연출 사진을 사용했으므로 독립 현장 평가로 보지 않는다.

제품은 아직 ‘자연어를 전반적으로 이해하는 작업 판단 시스템’이 아니다. 승인된 원문을 선택해 제시하고 근거 부족을 제한하는 MVP다. 같은 시연 사진에서 표현을 보태는 작업만으로 일반적인 정확성을 입증할 수 없다. 독립 표현·조건의 의미 평가를 R10·R11로 남겼다.

## 형식 오류 조사: 확인한 것과 모르는 것

초기 문제를 그대로 성공으로 덮지 않았다. 현재 프롬프트로 실제 진단 15회, 당시 문구를 복원한 비교 2회를 실행했다. 과거의 응답 형식 오류는 재현되지 않았다. 이 17회 중 상대 위치 질문 1회는 승인 인용 검증에서 실패했다. 이는 형식 오류와 구분해야 한다.

확인된 코드 결함은 `GroundedAnswer.model_json_schema()`가 모델 검증기의 상태별 제약을 포함하지 않는다는 점이다. 기존 생성 스키마는 다음과 같은 JSON을 허용했지만 서버는 거부했다.

- answered인데 근거가 없는 응답.
- 확인 대화가 아닌데 clarification_options가 있는 응답.
- 정보 부족·대상 없음·확인 요청 상태에 근거나 위치가 있는 응답.
- 사진 근거 없이 위치를 제시하는 응답.

통제된 계약 검사로 이 불일치를 재현했다. 이는 실제 코드의 원인 경로이며, 보존되지 않은 과거 3개 응답이 모두 같은 모순이었다는 증거는 아니다.

수정 중 처음 시도한 oneOf 스키마는 실제 요청 2회에서 HTTP 500을 반환했다. 이를 폐기했다. [Meta 공식 문서](https://dev.meta.ai/docs/structured-output)는 plain object 루트와 하위 anyOf를 지원하고 oneOf/allOf는 지원하지 않는다고 명시한다. 최종 구현은 `result.anyOf`와 `strict: true`를 사용한다. 상태별 필드 제약과 업무/사진 근거 범위를 생성 시점에도 전달하고, 서버의 모델·인용 검증은 계속 유지한다. 전송용 result 래퍼는 공개 API에 노출하지 않는다.

지금은 오류를 HTTP·응답 외피·종료 이유·JSON·필드 구조·상태 모순·승인 인용 단계로 구분한다. 예컨대 비확인 상태의 선택지는 `consistency/unexpected_options`로 기록한다. input/ctx를 그대로 직렬화하지 않으므로 예외 객체 직렬화 실패나 원문 유출을 피한다. 안전한 메타데이터만 표준 오류와 SQLite model_failures에 30일·최대 200건 보존한다. 키·사진·질문·모델 답변 원문은 진단 로그에 남기지 않는다.

## 최종 검증

- 자동 검사 **86개**: Python 81·JavaScript 5. 새 표현·재시도 연결, 생성 스키마의 상태 제약·Meta 지원 범위, 오류 단계·민감 데이터 제외, 재시작 뒤 진단 보존을 포함한다.
- 최종 지원 스키마의 실제 호출 **12건 오류 없음**: 직접 호환성 확인 2회 + 제품 API/브라우저 10회.
- 전체 조사에서 Meta에 보낸 HTTP 요청은 **31회**다. 여기에 수정 전 인용 검증 실패 1회와 폐기한 스키마의 HTTP 500 두 회가 포함된다. 청구 원장이나 일반 성공률을 뜻하지 않는다.
- 신규 SAM 호출과 모바일 검증은 하지 않았다. 기존 승인본 **4개**의 저장 내용 해시를 보존했다.
