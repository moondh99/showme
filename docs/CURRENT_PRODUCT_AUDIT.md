## 재현한 문제

### Q01 작성자가 키보드로 첫 강조 영역을 만들 수 없음

**P1 · 접근성.** 작성 화면에서 강조가 0개인 기존 평가용 안내서를 열고 ‘강조 영역 그리기’를 키보드로 활성화한다. Tab을 눌러도 사진에서 사각형을 만들 수 없다. ‘위치 세부 설정 · 0개 영역’을 펼치면 안내 문구만 있고 좌표 입력이나 추가 버튼이 없다.

사진 프레임에는 `tabindex`와 키보드 처리 경로가 없고, 생성은 포인터 시작·이동·종료에 의존한다. 숫자 입력은 이미 있는 강조를 편집할 때만 생긴다. 따라서 드래그를 못 하는 작성자가 첫 영역을 지정하려면 AI 생성 결과에 의존해야 한다. 강조 없이 승인할 수 있다는 사실은 수동 강조 생성 기능의 키보드 대안을 제공하지 않는다.

관련 코드: `web/app.js:62`, `web/app.js:82`. 규칙적인 사각형을 두 끝점으로 만드는 기능은 경로 자체가 필요한 자유 곡선 그리기 예외에 해당하지 않는다. [W3C 키보드 접근성 설명](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html).

수정안: 키보드로 누를 수 있는 ‘강조 추가’와 초기 사각형·이름·좌표 편집을 제공하거나, 사진에서 두 꼭짓점을 키보드로 선택하도록 한다. 0→1개 생성, 수정·삭제, 검토 해제, 기존 승인본 보존을 검증한다. 권장 작업: `$impeccable harden`.

### Q02 완료 확인에서 찾은 규칙이 검색 결과에 표시되지 않음

**P2 · 검색 결과 표시.** ‘평가용 · 장비 대여와 물품 보관’의 승인본에서 ‘교육’을 검색하면 1개 단계가 나온다. 그러나 결과에는 보관표/대여표의 용도를 적은 설명만 있고 ‘교육’ 문구가 없다. 실제 일치한 문구는 완료 확인의 ‘교육 이수 또는 책임자 동행’ 조건이다.

검색 함수는 제목·설명·완료 확인을 모두 검사하지만, 결과 그리기는 제목과 설명만 출력한다. ‘이 단계로 이동’을 누르면 조건을 읽을 수 있으므로 데이터 유실은 아니다. 다만 사용자는 왜 검색됐는지, 어디를 읽어야 하는지 다시 찾아야 한다.

관련 코드: `web/guide-search.js:6`, `web/app.js:211`. 수정안: 일치한 필드의 원문을 출처 이름과 함께 보여주고 해당 필드로 이동한다. 설명에 없는 검색어가 완료 확인에만 있을 때 결과에도 그 문구가 표시되는지 검사한다. 권장 작업: `$impeccable clarify`.

### Q03 모바일에서 답변 하나에 같은 규칙이 세 번 반복됨

**P2 · 반응형과 읽기 부담.** 파란 펜을 실제 SAM으로 선택하고 ‘이걸 서명하는 분께 건네도 되나요?’라고 물었다. 답변은 올바르게 금지했지만, 390×844에서 답변 카드 하나의 높이가 **981px**였다. ‘파란 펜은 운영자 메모용으로만 사용합니다’가 조건 카드, 관련 답변, 전체 승인 문맥에 반복됐다.

선택 후 사진은 문서 y=484px, 질문 입력은 y=1452px, 답변 시작은 y=1605px였다. 답변 안의 ‘이 질문의 선택 다시 보기’는 y=2527px에 있다. 가로 넘침은 없었으나 선택한 사진과 답변을 함께 보기 어렵다. 처리 완료 시 마지막 카드 전체를 대상으로 스크롤하고, 질문 입력은 대화 목록 앞에 있어 연속 질문에서도 왕복이 필요하다. 실제 사람의 혼동률이나 읽기 시간을 측정한 결과는 아니다.

관련 코드: `web/app.js:162`, `web/app.js:168`, `web/app.js:181`, `web/app.js:265`. 원문 보존은 이전 결함 수정의 보호 장치이므로 단순히 접거나 삭제하는 변경은 적절하지 않다. 우선 판정·대상·적용 조건을 한 번에 읽도록 묶고, 원문 전체의 접근성과 조건 보존을 유지하면서 중복 표현을 줄이는 시안을 비교한다. 권장 작업: `$impeccable distill`.

## 제품 판단과 남은 검증

현재 안내서 전체에는 답이 있지만 현재 단계에는 없는 경우도 남는다. 전체 배치 단계에서 펜의 서명 용도를 물으면 올바르게 유보하고, ‘서명’ 검색으로 도구 준비 단계의 규칙을 찾을 수 있다. 이 유보도 작성자의 보완 목록에 들어간다. 실제 내용 누락과 다른 단계에 있는 답을 구별하면 작성자의 불필요한 재검토를 줄일 여지가 있다. 이번에는 검색 이용으로 보완 항목이 자동 해결된다고 주장하지 않는다.

핵심 가치인 ‘처음 온 사람이 사진에서 가리켜 작업 규칙을 찾는다’는 내부 시연으로 확인했다. 정적 사진 안내서보다 작업 완료가 빨라지는지, 담당자의 준비·보완 시간이 줄어드는지, 10~20초를 기다린 뒤 긴 답변을 읽을 만한지는 아직 검증하지 않았다. 이는 검사 수를 늘려 대신할 수 없는 다음 제품 검증이다.

수정 순서는 Q01의 키보드 대안, Q02의 일치 문구 표시, Q03의 중복 독해 완화다. 마지막에 `$impeccable polish`로 정리하고 `$impeccable audit`로 다시 확인한다. 실제 사람에게 정적 안내서와 비교하는 작업, 현장 사진, 외부 배포·영상·제출은 기존 I11~I15와 R12에 계속 남아 있다.

## 점검 도구와 원본

Impeccable의 문맥 로더는 실행 권한으로 실패해 기존 제품 기획과 소스를 직접 읽었다. 기술 점검인 audit 경로로 진행했으며 독립 디자인 비평 두 건을 수행했다고 주장하지 않는다. 번들 탐지기는 셸로 실제 실행했고 6개 스타일 경고를 반환했다. 하나는 실험용 `sam-probe.html`, 나머지는 카드의 강조 테두리였다. 본체 HTML의 `/static/style.css`를 파일 경로로 연결하지 못해 색 관련 검사가 불완전했다. 이 경고들은 작업 실패를 재현하지 못했으므로 위 3개 결함 수에 넣지 않았다.

모바일 설정이 다른 활성 탭에 적용된 중간 측정 1회는 1632px임을 확인해 폐기했다. 작성자 탭을 닫고 실제 `innerWidth=390`, `innerHeight=844`를 확인한 수치만 모바일 근거로 사용했다. 점검용 탭과 화면 크기 설정은 종료 시 정리한다. 기존 서버는 그대로 유지한다.

로컬 근거: `state/evidence/product-audit-v1/`의 호출 전 계획, A01~A06 응답, B01 선택·질문 지표, 검색 결과, 모바일 측정·화면, 승인본 전후 해시, `summary.json`. 비밀과 요청 사진 payload는 보고서에 포함하지 않았다.
