# R10·R11 평가 세트·수정·실제 검증

2026년 11월 2일. 기준 `953d414`. [고정 평가 세트와 실행 자료](../evaluations/r10-r11-v1/README.md)를 먼저 만들고 수정했다. 이전 질문을 바꾸어 반복한 사례만으로 일반화를 주장하지 않도록 작업 규칙도 바꿨다.

## 수정 전 발견

새 discovery 12개에서 목적 분류는 8/12, 응답 상태는 9/12였다. ‘사용하는 … 생김새’처럼 업무 단어를 포함한 사진 질문을 업무로 고정하거나, 새 외형 표현을 사진 질문으로 읽지 못했다.

적용 질문 7개는 관련 승인 규칙을 대체로 인용했다. 그러나 동일한 규칙을 조건 충족·미충족 모두에 제시했고, 사용자 상황의 적용 결과가 별도로 없었다. 이를 ‘의미 정확도 0%’나 실제 잘못된 허용 7건으로 기록하지 않는다. 새 평가의 구조화된 판단 계약이 기존 기능에는 없었다는 점을 구별한다.

## 변경

### R10 — 질문 의미로 목적 결정

기본 제품 서비스는 새 `answer_with_reasoning`이다. 새 자동 질문의 목적은 표현 정규식으로 확정하지 않고, 질문이 요구하는 정보와 대상을 모델이 함께 해석한다. ‘장비 대여용으로 쓰는 표가 놓인 통의 생김새’는 목적을 설명하는 명사구가 포함돼도 사진 정보 요청으로 처리한다.

정규식은 과거 클라이언트의 명시적 사진 목적 보호와 기존 주입 서비스의 호환 힌트로 남았다. 기본 자동 요청은 그 힌트에 고정되지 않으며, 서버는 실제 결정된 목적을 저장하고 확인 대화에서 이어간다. 기존 단일 호출 answer_question은 과거 평가의 비교 경로로 유지한다.

### R11 — 대상·조건의 적용 결과와 검토

모델이 대상과 policy/allowed/blocked/conditional/unknown을 구조화하고 적용 조건을 승인 원문에서 인용한다. 질문에 없는 확인 사실을 충족됐다고 가정하지 않는다. AND·OR·금지·예외·다른 필드의 제한과 선택 지점의 대상을 함께 다룬다.

자동/업무 질문은 두 번째 모델 호출에서 원래 사진·승인본·질문과 후보 판단을 다시 검토한다. 같은 모델을 다른 프롬프트로 호출하는 일관성 검사이며, 독립된 사람이나 형식 논리 검증기가 아니다. 판정이 정확하다는 보증으로 표현하지 않는다.

서버는 최종 인용과 조건 문구가 실제 승인 필드에 있는지 검사하고, 조건도 기본 답변의 인용에 포함한다. allowed인데 근거 조건이 없거나 unknown이면 conditional, 명시적 미충족이면 blocked로 제한한다. 검토 호출이 실패했을 때 검토하지 않은 초안을 대신 반환하지 않는다. 명시적인 사진 전용 요청에는 승인 업무 규칙을 전달하지 않는다.

화면은 대상·판정과 관련 승인 기준을 보여준다. ‘질문에 적힌 상황을 가정한 AI 판정’임을 밝히며 실제 확인 완료나 작업 완료를 자동 승인하지 않는다. 금지 조항의 적용을 ‘충족’이라고 표시하면 허용으로 오해될 수 있어, 브라우저 검토 후 근거 문구와 전체 판정의 표현을 구분했다. 이 표현 수정은 모델 판정 로직을 바꾸지 않았다.

## 세트와 결과

28개를 구현 전에 고정했다. 수정용 12개, 중간 검증 8개, 최종용 8개로 나눴다. 기존 커밋의 소스·검사·문서·평가와 정확히 같은 질문은 0개였다. 질문·기준은 Codex가 작성했으며, 외부 블라인드 평가가 아니다. 알려진 AI 연출 사진을 사용했으므로 새 사진 일반화 평가도 아니다.

| 단계 | 목적/상태 일치 | 대상·판정 일치 | 의미 |
|---|---:|---:|---|
| 수정 전 12개 | 목적 8/12, 상태 9/12 | 판정 필드 없음 | 수정의 비교 기준 |
| 수정 후 12개 | 12/12 | 7/7 | 수정용 회귀 |

최종 8개의 결과로 모델/프롬프트를 다시 조정하지 않았다. 최종 실행 manifest에 해당 시점의 추론/API 소스 해시를 보관했다. 이후 생성 스키마에 이미 있던 목적·상태·판정 일관성 제약을 런타임에도 추가했다. 프롬프트·질문·규칙·판정 알고리즘은 바꾸지 않았고, 저장된 평가 28개와 실제 앱 4개 응답을 재생해 새 검사를 통과함을 확인했다. 이 재생은 새 모델 평가가 아니다. 수정용·중간 검증은 개발 중 버전의 기록이므로 세 단계를 하나의 완전한 블라인드 정확도로 합치지 않는다.

허용 조건이 붙는 질문은 전체 단계에 16개, 용도 질문까지 포함한 구조화된 대상·판정 항목은 17개였다. 금지/조건부를 허용으로 판정한 경우는 관측한 12개에서 0개였다. 특히 최종용에서는 4개 중 0개였다. 작은 내부 세트이므로 일반 오류율 0%로 해석하지 않는다.

인용 검사는 전체 문맥 펼치기 내용을 정답 근거로 세지 않는다. 자동 판정 외에 AND 대조, OR 대조, 미확인 조건, 다른 대상의 규칙 전용, 없는 규칙을 내부 검토했다. 기록은 results/internal-review.json에 있다. 개별 조건의 상태 표시는 자연어 제약 해석을 포함하며, 형식 논리의 원자 명제 증명이 아니다.

## 실제 API·브라우저

오프라인 평가에서 실제 Muse 68회(수정 전 12, 수정 후 24, 중간 16, 최종 16)를 호출했다. 제품 브라우저에서 추가 Muse 8회와 SAM 1회를 실행했다. 총 **Muse 76회·SAM 1회**이며, 질문 수·모델 호출 수·자동 검사 수를 구별한다.

제품 흐름은 다음 4개를 확인했다.

1. 업무 명칭이 섞인 외형 질문 → 사진 답변으로 노란 트레이를 표시.
2. 교육 미이수지만 책임자 동행 → OR 조건에 따라 allowed.
3. 교육 확인도 동행 책임자도 없음 → blocked.
4. 실제 SAM으로 파란 보관표 선택 후 교육 이수를 이유로 장비 반출 요청 → 선택한 대상은 보관표임을 확인하고 대여 금지 규칙으로 blocked. 노란 대여표의 권한을 옮기지 않음.

네 응답의 목적·대상·판정과 실제 서버 저장을 확인했다. 브라우저 콘솔 경고·오류는 없었다. 기존 승인본 **6개**의 저장 내용 해시를 보존하고 평가용 안내서 1개만 별도로 승인했다. 테스트에 사용한 공개 연출 사진 외의 자료는 전송하지 않았다.

자동 검사는 **98개(Python 93·JavaScript 5)** 통과했다. 올바른 원문을 잘못된 대상의 근거로 삼는 후보의 교정, 미확인/근거 없는 allowed 제한, 위조 조건 인용 차단, 검토 실패 시 답변 유보, API의 의미 기반 목적 저장, 고정 세트 해시·채점 경계를 포함한다.

## 비용과 남은 한계

현재 단계 28개에서 대기 중앙값 **23.051초**, 최대 **57.890초**였다. 최종용 8개는 중앙값 22.821초·최대 37.613초였다. 두 작업자 실행의 관측값이며 일반적인 응답 시간 보장이 아니다. 단일 호출이던 비교 12개는 중앙값 8.740초였다. 정확성 검토를 위해 일반 자동/업무 질문당 두 번 호출하는 지연·사용량 비용이 생겼다. 계정 청구 금액이나 잔액은 조회하지 않았다.

같은 모델은 같은 오해를 반복할 수 있다. 사전 작성된 기대 판정과 맞았다는 결과가 규칙 의미의 일반 정확성이나 현장 안전성을 입증하지 않는다. 독립된 사람의 정답 검수, 새 사진과 실제 작업, 사용자의 대기·독해 비용 관찰, 외부 배포·제출은 남아 있다. 지연 개선은 별도 R12로 남겼다.
