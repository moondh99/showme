# ShowMe 최종 제출 전 비평 — 2026년 11월 3일

**현재 그대로 최종 제출하는 것은 권하지 않는다. 핵심 기능은 제출할 가치가 있는 MVP지만, 심사위원에게 전달할 완성본은 아직 아니다.** 사람 검증은 사용자 요청에 따라 이번 해커톤의 필수 조건에서 제외한다. 다만 실사용 효과는 미검증으로 남긴다. 이 평가는 제출 자격에 대한 주최 측의 판정이나 수상 확률이 아니다.

평가 대상은 현재 작업 공간의 수정본이다. 디자인 평가와 구현·탐지기 평가는 서로 결과를 보지 않는 두 평가자가 수행했다. 부모 평가자는 실제 Meta 연결, 승인본 고정, 공식 제출 안내를 추가 확인했다. 배포는 사용자 요청에 따라 보류했으며 비평 도중 제품 소스는 수정하지 않았다.

## 가장 먼저 고쳐야 할 5가지

### 1. [P0 · 제출 준비] 필수 산출물이 아직 없다

공식 안내에서 **공개 소스 저장소와 3분 데모 영상**을 확인했다. 현재 프로젝트에는 공개 저장소 주소가 연결돼 있지 않고, 최종 영상도 없다. 기존 약 4분 대본은 그대로 사용할 수 없다. 로컬 주소는 다른 컴퓨터의 심사위원이 접속할 수 있는 체험 주소도 아니다.

행사 기간에 직접 만든 기능·코드·기여를 영상에서 분명히 구별해야 한다. 공개 저장소·접근 가능한 3분 영상·행사 중 개발한 범위·직접 열리는 체험 경로를 준비하고 실제 제출 폼에서 마지막으로 대조해야 한다. 영상의 언어·개별 입력 필드·추가 첨부 요건까지 확인했다고 주장하지 않는다. [공식 참가자 안내](https://cerebralvalley.ai/e/meta-ai-developer-hackathon/details#7-submission-process-15)

### 2. [P1 · 제품 설득력] 예쁜 이미지 질문 앱으로 읽힐 위험이 크다

공식 안내는 피해야 할 예시로 Basic RAG Applications와 Simple Image Analyzers를 든다. ShowMe가 해당 유형으로 확정 분류되거나 실격된다는 뜻은 아니다. 그러나 ‘사진을 올리고 AI에게 질문한다’로 소개하면 주최 측이 피하라는 인상을 줄 위험이 있다.

현재 접수대의 펜·트레이 색 구분은 기능 설명에는 쉽지만, 그 문제에 왜 10초 이상 AI를 기다릴 가치가 있는지 설득력이 약하다. 심사위원의 질문은 ‘무엇을 인식했나’보다 ‘사진과 설명을 그냥 읽으면 안 되는 이유가 무엇인가’일 것이다.

시연의 중심은 **이름 모르는 물체 선택 → SAM 윤곽 → 담당자 승인 규칙 연결 → 다른 대상의 규칙을 잘못 적용하려는 요청의 차단**으로 잡는 편이 타당하다. 승인·수정·고정·문맥 보존이 실제로 작동하는 것도 함께 보여줘야 한다. 실제 사용자 효과를 대신 입증한다고 표현하지 않는다. [공식 주의 유형·심사 기준](https://cerebralvalley.ai/e/meta-ai-developer-hackathon/details#sample-anti-projects-9)

### 3. [P1 · 작성 흐름] 작성자 화면은 아직 반복 작업을 편하게 처리하지 못한다

저장·검토·단계 이동 때 화면 전체를 다시 만들면서 키보드 초점이 BODY로 돌아간다. 독립 평가자 두 명과 부모 점검에서 재현했다. 강조 영역을 추가하면 이름에 초점이 가는 개선은 확인됐지만, 저장하고 다시 편집할 때는 긴 페이지에서 위치를 다시 찾아야 한다. 관련: `web/app.js:54–56`, `77–82`, `151`.

행동 메모는 왼쪽 큰 사진 아래에 있고, 강한 파란 AI 생성 버튼은 오른쪽 위에 있다. 메모를 먼저 입력해야 하지만 생성 버튼을 먼저 보게 되는 구조다. 메모 누락은 차단하므로 잘못된 API 요청을 일으킨다고 주장하지 않는다. 잘못된 순서로 유도한 뒤 오류 안내로 되돌리는 사용성 문제다. 데스크톱 편집 페이지도 약 2,500px 길이였다.

저장·검토 후 초점과 펼침 상태를 유지하고, 메모와 생성 행동을 같은 작업 구역에 두어야 한다. 좌표 입력에는 범위와 단위 설명도 필요하다. 권장 작업: `impeccable harden`, `impeccable layout`.

### 4. [P1 · 모바일 정보 구조] 가로 넘침이 없다는 사실을 사용성 완성으로 착각하면 안 된다

부모 평가자의 실제 선택·질문 응답을 390×844에서 측정했다. 사진은 문서 y≈524px, 질문 제목은 y≈1,507px, 답변은 y≈1,901px에서 시작했다. 답변 카드 하나가 약 991px였다. 물체 선택 후 질문으로 자동 이동하고 사진 복귀 버튼도 있지만, 사진과 승인 조건·질문을 함께 읽으려면 여전히 왕복해야 한다.

중복 인용은 줄었고 승인 원문 전체도 보존됐다. 그 자체로 읽기 부담이 해결된 것은 아니다. 단계 메모의 본문은 15px, 완료 조건은 13px로 작다. 실제 지켜야 할 내용보다 사진과 보조 요소가 넓은 영역을 차지한다. 관련: `web/pinboard.css:84`, `87`, `96–100`.

조건·예외 원문을 감추거나 글자를 줄이는 방식으로 해결하면 안 된다. 모바일의 이전·다음 사진 카드와 보조 안내를 압축하고, 선택 대상·질문·판정을 가까이 배치하면서 업무 본문을 최소 16px로 읽게 해야 한다. 이 수치는 다른 질문이었던 이전 981px 카드와 성능 개선율로 비교하지 않는다. 권장 작업: `impeccable adapt`, `impeccable distill`.

### 5. [P2 · 배포 기능] 보이는 샘플 버튼이 배포 묶음에서는 실패한다

샘플 사진 API는 `experiments/meta-vision/inputs/notepad.jpg`를 필요로 하지만, 새 Dockerfile은 이 파일을 포함하지 않는다. Dockerfile과 같은 파일 배치를 임시 폴더에 만들고 실제 앱 요청을 실행하자 샘플 추가가 404와 ‘샘플 사진이 없습니다’ 안내로 실패했다. 직접 사진 업로드는 대안이므로 제품 전체의 P0로 과장하지 않는다.

이는 컨테이너 실제 실행 결과가 아니다. Docker 엔진이 실행 중이 아니어서 동일한 패키지 내용의 호스트 실행으로 확인했다. 라이선스를 갖춘 샘플을 배포 파일에 명시적으로 포함하거나, 없는 환경에서는 버튼을 제공하지 않아야 한다. 관련: `src/showme/app.py:209–211`, `Dockerfile:6–9`. 권장 작업: `impeccable harden`.

## 유지할 강점과 남은 관찰

Pinboard의 사진·노란 승인 메모·실제 앞뒤 단계 사진은 이 제품에 맞는 시각 언어다. 작성 화면을 평범한 관리 도구라고 해서 무조건 다시 디자인할 필요는 없다. 승인 원문과 AI 해석을 구별하고 전체 조건·예외를 계속 표시하는 방향도 유지할 가치가 있다. 승인본 고정·권한 경계·단계별 요청 격리는 실제 제품의 강점이다.

처음 쓰는 작성자는 메모보다 먼저 보이는 생성 행동 때문에 순서를 오해할 수 있다. 키보드 작성자는 저장·검토·단계 전환마다 위치를 잃는다. 작업 중 자주 중단되는 학습자는 새로고침하면 선택·질문 초안·대화 맥락을 다시 만들어야 한다. 대화 손실은 화면에 고지되고 설계에 명시된 제약이므로, 숨은 데이터 유실 버그와 구분한다.

인지 부담은 작업 기억·한 번에 한 결정·선택 최소화에서 약하다. 작성 사진 도구에는 사진 교체·그리기·영역 추가·전체 삭제·세부 설정의 다섯 행동이 있다. 사진에서 물체를 고르는 순간이 대표 장면이지만, 긴 편집과 긴 답변이 그 앞뒤를 무겁게 한다. 전체 완료의 끝맺음도 완료 표시 문장에 머문다.

작성자/학습자의 로고·색상 차이는 P3 수준이다. `/static/research/sam-probe.html`이 공개되고 제품에 SAM이 연결되지 않았다는 오래된 설명을 유지하는 점도 정리 대상이다. 연결선 토글과 장식 다듬기에 우선순위를 더 쓰기보다 핵심 질문 경험을 앞당겨야 한다.

정적 탐지기는 경고 6개를 냈다. 한 건은 연구 페이지, 네 건은 덮어쓴/사용하지 않는 선언, 한 건은 실제 상태 안내용 강조여서 여섯 개의 사용자 결함으로 세지 않았다. 스타일시트 경로 해석이 불완전하고 실제 색 대비 전수 검사는 하지 못했다. 이번 브라우저 도구는 DOM 변경을 허용하지 않아 오버레이를 주입하지 않았고, DOM·접근성 트리·화면을 직접 점검했다. 표시되는 오버레이가 있다고 주장하지 않는다.

**제출 전 우선순위:** 필수 공개 저장소·3분 시연 계획 확정 → 배포 샘플 누락과 작성자 초점 복구 → 모바일 핵심 동선 정리 → 실제 외부 배포 검증·3분 촬영 → 최종 `impeccable polish`와 고정본 재확인. 사람 검증은 이번 필수 작업에 다시 넣지 않는다.

원본 근거: `state/evidence/final-critique-v1/`. 실제 응답·호출 전 계획·화면·탐지기·패키지 재현·승인본 해시·소스 해시를 보관했다. 임시 브라우저 탭을 닫고 화면 크기 설정을 복구했으며, 평가용 8766 서버를 종료했다. 본 서버 8765는 유지했다.
