# ShowMe 제품 결정 기록

ShowMe는 담당자가 승인한 사진 안내서를 처음 맡은 사람이 따라 할 수 있게 만든 도구다. 사용자는 설명을 읽고, 이름을 모르는 물체는 사진에서 가리켜 질문하고, 기준을 직접 확인한 뒤 완료를 표시한다. 이 문서는 포트폴리오에서 문제 발견, 선택한 설계, 확인 방법을 설명할 수 있도록 그 근거를 보관한다.

## 제품의 판단 경계

| 결정 | 선택한 이유 | 남은 제약 |
| --- | --- | --- |
| 초안과 승인본을 분리한다 | 작업자가 보고 있는 절차가 담당자의 편집 도중 바뀌면 어느 지시를 따랐는지 설명하기 어렵다. 승인 시점의 사진·순서·문구를 한 버전으로 고정했다. | 기존 승인본에 오류가 발견되면 새 승인본을 만들어 전달하는 운영 절차가 필요하다. |
| 사진의 대상 선택과 규칙의 적용을 구별한다 | 물체의 윤곽은 무엇을 가리켰는지 좁혀 주고, 용도나 허용 여부는 담당자의 문구가 결정한다. 답변에 관련 문장과 전체 승인 원문을 남겼다. | 대상 연결과 조건 해석에는 모델 판단이 들어간다. 원문 검증은 인용을 확인하는 장치이며 적용 판단의 정확도는 별도로 평가해야 한다. |
| 완료는 작업자가 확인하고 표시한다 | 안내서가 보여주는 사진은 작업 기준을 설명한다. 작업을 수행한 사람만 현재 현장에서 기준이 충족됐는지 확인할 수 있다. | 완료 수치는 브라우저에 저장된 표시이며, 작업 성과나 실수 감소를 측정한 값으로 쓰기 어렵다. |

구현 근거는 [제품 명세](PRODUCT_SPEC.md), [물체 선택 검증](SELECTION_RESULTS.md), [규칙 판단 검증](R10_R11_RESULTS.md)에 있다.

## 2026년 11월 3일 · 모바일의 작업 순서를 다시 설계

이전 수정에서는 사진 다음에 질문란을 두어 사진에서 질문까지의 거리를 줄였다. [제출 전 재평가](FINAL_SUBMISSION_CRITIQUE.md)에서 질문과 답변이 누적될수록 승인 메모와 완료가 뒤로 밀리는 문제를 확인했다. 같은 단계를 읽고 마치는 사람도 대화 영역을 지나야 했고, 완료 후에는 위로 이동해 다음 단계를 찾아야 했다.

### 결정 1. 사진 다음에 승인 메모와 완료 행동을 둔다

모바일과 키보드의 읽기 순서를 사진 → 승인 메모·완료 → 질문 → 주변 단계로 맞췄다. 데스크톱에서는 사진과 메모를 나란히 놓는다. 같은 원문을 두 군데 복제하면 수정 시 문구가 어긋날 수 있어 한 영역을 화면 폭에 따라 배치했다.

질문 입력란은 문서상 더 아래에 놓이게 됐다. 390px의 2단계에서 사진 상단은 약 453px, 승인 메모는 854px, 질문 제목은 1,363px에 있었다. 질문 제목의 이전 측정치는 약 871px였다. 텍스트 질문까지의 거리가 늘어나는 대신 승인 지시가 질문 이력의 길이에 영향을 받지 않는다. 사진에서 물체를 고르면 질문 제목으로 이동하며, 메모에도 질문 바로가기를 뒀다.

### 결정 2. 완료 표시와 다음 단계 이동을 분리하고 나란히 둔다

완료 표시와 동시에 화면이 넘어가면 완료 기준을 다시 읽거나 표시를 되돌리기 어렵다. 완료 버튼에 초점을 남기고 그 옆에 ‘다음 단계로’를 노출했다. 마지막 단계에서 앞 단계가 남아 있으면 ‘미완료 단계로’를 제공한다. 모든 단계의 완료 표시는 마지막으로 표시한 메모 안에서 확인한다.

### 결정 3. 비동기 응답이 도착했을 때 사용자가 읽던 위치를 존중한다

사진 선택과 질문 시작 시 대기 상태에 초점을 둔다. 응답이 도착할 때도 초점이 대기 상태에 있으면 결과나 오류 안내로 옮긴다. 기다리는 동안 승인 메모나 검색으로 옮긴 사람은 그 위치에서 작업을 이어갈 수 있도록 초점, 열린 상세 영역, 검색 입력을 복원한다. 버튼과 Esc로 선택을 취소했을 때의 복귀 위치도 같게 맞췄다. 실패한 질문은 입력을 남겨 재시도할 수 있다.

### 결정 4. 첫 줄에 대상과 판정을 붙이고 승인 원문을 이어 보여준다

이전 답변은 판정 이름과 확인한 대상이 서로 다른 줄에 있었고, 사진으로 돌아가는 버튼이 판정보다 먼저 나왔다. 지금은 ‘파란 펜 · 질문에 적힌 상황에서는 진행할 수 없어요’처럼 같은 줄에 두고, 대상 사진으로 돌아가는 버튼을 근거 뒤에 배치했다. 문장을 새로 요약하는 모델 호출을 추가하면 승인 원문에 없는 예외나 허용 범위가 생길 수 있다. 기존 구조화된 대상·판정만 조합하고, 승인 설명과 완료 확인의 전체 원문을 기존 방식으로 표시한다.

## 확인한 범위

- 기본 자동 검사 Python 113개와 JavaScript 16개를 실행했다.
- 브라우저에서 320px·390px·900px 너비와 기본 데스크톱 화면을 점검했다. 320px·390px·900px에서 가로 넘침은 관찰되지 않았다.
- 키보드로 선택 취소, 원문 제목으로 이동, 완료 후 다음 단계 이동, 마지막 단계에서 미완료 단계로 돌아가기, 전체 완료 표시를 확인했다.
- 테스트용 모델 응답으로 성공 판정 초점, 승인 원문 일치, 오류 시 입력 복원, 답변 도착 후 승인 메모와 검색의 초점 유지를 확인했다. 테스트 화면과 측정값은 로컬의 `state/evidence/portfolio-learner-flow/`에 보관했다.
- 이 변경의 검증 범위는 브라우저 동작과 표현이다. 모델의 의미 정확도와 지연에는 [이전 실제 API 검증](SUBMISSION_FIXES_RESULTS.md)이 적용된다. 대표 선택 질문 두 건의 모델 처리 시간은 14.120초와 19.757초였고, 실물 휴대전화와 스크린리더 검증은 남아 있다.

## 다음에 검증할 제품 판단

1. 비슷한 물체에 서로 다른 예외가 적용되는 작업에서 승인 문구를 읽는 과정과 사진으로 가리켜 확인하는 과정을 비교한다. 선택 대상, 답변, 원문 조건, 불확실한 지점을 함께 기록한다.
2. 실측 지연이 길었던 요청에서 사용자가 안내서를 이어 읽을 수 있는지 확인한다. 속도 변경은 동일한 사례에서 판정과 예외가 유지되는지 함께 평가한다.

## 2026년 11월 3일 · 같은 탭에서 질문을 이어가기

작업 중 화면을 새로고침하면 완료 상태와 현재 단계는 돌아왔지만, 방금 가리킨 물체와 확인 질문은 사라졌다. ‘이 물체’처럼 대상이 입력에 적히지 않은 질문은 문장만 남겨도 안전하게 이어 쓰기 어렵다. 그래서 **선택 윤곽·대상 확인 흐름·입력 중인 질문을 한 단위로 복원**했다.

- 단계별로 화면에 표시하는 최근 답변 8개, 입력, 선택을 승인 링크와 단계 ID로 구분한다. `sessionStorage`를 사용해 같은 탭의 새로고침을 지원한다. 복원 기한은 해당 단계의 기록을 처음 저장할 때부터 최대 24시간이며, 편집해도 늘어나지 않는다. 서버에서 확인 대화와 선택을 사용할 수 있는 시간에 맞춘 범위다.
- 응답을 기다리던 요청은 입력으로 돌려준다. 새로고침 전에 서버가 이미 처리했을 수도 있으므로, 사용자가 확인한 뒤 다시 보내도록 했다. 새로고침 이전 요청의 응답을 나중에 찾아오는 기능은 없다.
- ‘이 단계의 대화 지우기’는 이 탭에서 해당 단계의 질문·입력·선택만 지운다. 다른 단계의 입력과 완료 표시는 이어서 사용할 수 있다. 작성자 보완 목록과 서버의 질문 보관은 별도다.
- 브라우저가 저장소 접근을 차단하면 열린 화면 안에서 질문할 수 있다. 24시간은 화면 복원 기준이다. 만료 데이터는 해당 승인본을 다시 열거나 해당 단계의 캐시를 갱신할 때 정리한다.

### 확인한 범위

| 상황 | 관찰 |
| --- | --- |
| 390px 화면에서 대상 확인 답변을 작성한 뒤 새로고침 | 2단계, 선택 윤곽, 확인 질문 1개, 작성 중이던 답변이 복원됐다. 이어서 전송해 승인 원문이 메모와 일치하는 답변을 받았다. |
| 응답 대기 중 새로고침 | 이전 답변 2개와 입력이 복원됐다. 대기 카드는 사라졌고 요청을 다시 보내려면 버튼을 눌러야 했다. |
| 같은 주소를 독립적으로 연 탭 | 입력·대화·윤곽이 비어 있었다. 브라우저의 탭 복제나 닫은 탭 복구는 별도로 확인하지 않았다. |
| 320px 화면에서 키보드로 기록 지우기 | 보관 안내 제목으로 초점이 이동했다. 새로고침해도 지운 기록은 돌아오지 않았고, 완료 표시와 3단계 입력은 복원됐다. 가로 문서 폭은 320px이었다. |
| 자동 검사 | Python 113개, JavaScript 19개. 추가 검사에서 최근 8개 제한, 승인 링크·단계 격리, 고정 만료와 저장 불가 시 동작을 확인했다. |

화면 검증에는 별도 임시 서버와 고정 응답을 사용했다. 실제 모델 지연과 정확도는 이번에 측정하지 않았다. 화면과 관찰값은 `state/evidence/portfolio-conversation-resume/`에 있다.

## 2026년 11월 3일 · 파란 보관표에 장비 대여 조건이 잘못 적용되는지 확인

기존 평가용 안내서에서 파란 트레이의 보관표를 선택한 뒤 “교육을 받았으니까 이 표로 장비를 가져가겠습니다.”라고 질문했다. 기대한 결과는 파란 표를 보관표로 연결하고 반출을 막는 것이다. 교육 이수 또는 책임자 동행은 노란 장비 대여표의 발급 조건이다.

| 경로 | 확인한 결과 |
| --- | --- |
| 승인 메모 직접 읽기 | 설명에 “보관표로 장비를 대여할 수 없습니다.”가 명시되어 있다. 표를 이미 구별할 수 있으면 이 문장만으로 결정을 내릴 수 있다. |
| 사진에서 가리켜 질문하기 | SAM 3.1이 클릭한 보관표의 윤곽을 표시했다. Muse Spark 1.3은 대상을 ‘파란 트레이의 보관표’로 특정하고 진행 불가로 판정했다. 화면과 서버 답변의 승인 설명·완료 확인은 승인본 원문과 각각 일치했다. |
| 승인 메모를 읽으며 기다리기 | 질문 직후 승인 메모 제목으로 이동했다. 판정이 도착한 뒤에도 제목에 초점이 있었고 화면 위치는 706px로 같았다. 같은 탭에서 새로고침한 뒤에도 실제 판정 1건과 선택 윤곽이 복원됐다. |

390×844 브라우저에서 클릭과 전송 이벤트부터 결과가 화면에 들어가는 시점까지 측정했다. 테스트용 HTML에 계측 스크립트를 붙였으며 학습 화면과 API는 현재 구현을 사용했다.

| 구간 | 시간 |
| --- | ---: |
| 사진 클릭 → 선택 윤곽 표시 | 3.865초 |
| 질문 전송 → 판정 표시 | 22.093초 |
| 사진 클릭 → 판정 표시, 자동 입력 간격 포함 | 26.402초 |
| 제공자 처리 지표 | SAM 3.400초, Muse 22.070초(2회) |

계측 스크립트를 처음에 인라인으로 넣어 앱의 브라우저 보안 정책에 차단됐다. 스크립트를 같은 서버의 별도 파일로 옮긴 뒤 같은 보관표를 다시 선택했다. 두 선택의 좌표는 각각 240/643과 240/639로 약간 달랐고 반환된 영역은 동일했다. 총 사용량은 실제 SAM 2회와 Muse 2회다. 표의 브라우저 시간은 두 번째 선택부터 시작한다. 임시 서버에 기존 승인본과 사진만 복제했고 원본 승인 문서와 일치하는 것을 확인했다.

이 사례가 보여주는 가치는 **사진에서 가리킨 대상을 승인 규칙에 연결해, 다른 물체에 적용되는 조건을 잘못 옮기는 일을 막는 것**이다. 금지 문장이 이미 짧고 직접적이므로, 승인 메모를 읽는 경로의 이점도 분명하다. 화면에서는 노란 표의 발급 조건도 ‘판정에 사용한 승인 기준’이라는 같은 이름으로 강조됐다. 핵심 금지 근거와 다른 물체의 조건을 읽는 순서가 더 명확해질 여지가 있다. 한 건의 연출 사진 검증이며 실제 작업자의 시간 절감이나 오류 감소를 측정하지 않았다.

화면과 측정 원본은 `state/evidence/portfolio-live-scenario/`의 `mobile-selection.png`, `mobile-reading-during-wait.png`, `mobile-verdict.png`, `results.json`에 있다. 앞선 [지연 개선 검증](R12_TAIL_RESULTS.md)의 모델 호출 합계와 이번 브라우저 구간 측정은 기준이 다르다.

## 2026년 11월 3일 · 금지 이유와 다른 표의 조건을 나눠 보여주기

앞선 실제 검증에서 모델은 파란 보관표에 대한 반출 요청을 올바르게 막았다. 화면에서는 제목에 ‘질문에 적힌 상황에서는 진행할 수 없어요’까지만 나왔다. 파란 표의 금지 문장과 노란 대여표의 발급 조건은 모두 ‘판정에 사용한 승인 기준’으로 강조됐다. 두 표를 헷갈려 질문한 사람에게 규칙을 다시 분류하게 하는 화면이었다.

| 항목 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 판정 제목 | ‘파란 트레이의 보관표 · 질문에 적힌 상황에서는 진행할 수 없어요’ | ‘파란 트레이의 보관표 · 진행 불가. 보관표로 장비를 대여할 수 없습니다.’ |
| 파란 표의 금지 문장 | 다른 인용과 같은 이름으로 강조 | ‘진행 불가 근거’로 표시하고, 승인 원문에서 확인한 문장을 제목에 인용 |

모델이 기존 두 번의 판단 과정에서 인용의 역할을 함께 반환하도록 했다. 서버는 인용이 해당 승인 필드에 실제로 있는지 확인한다. 다른 대상의 기준은 현재 대상의 허용 조건을 충족시키는 데 쓰지 않는다. 단독으로 인용하면 예외가 빠질 수 있는 문장과 금지 이유를 하나로 특정할 수 없는 답변은 전체 원문에서 확인하도록 했다. 이전에 저장한 응답에 인용 역할이 없으면 일반 판정 제목과 원문을 계속 보여준다.

### 검증 결과

- 같은 승인본과 사진을 복제한 임시 서버에서 파란 표를 선택하고 이전과 같은 질문을 보냈다. 초기 응답을 확인한 뒤 프롬프트에서 시연 사례와 같은 예시를 빼고 최종 코드에서 한 번 더 실행했다. 두 실행을 합해 실제 SAM 3.1 2회와 Muse Spark 1.3 4회를 사용했다. 최종 응답도 보관표 반출을 막았고, 금지 문장과 노란 표의 발급 조건은 기대한 역할로 돌아왔다.
- 390px 화면에서 응답이 도착하면 금지 이유가 담긴 제목에 초점이 갔다. 320px에서 다른 대상의 기준 링크를 키보드로 열어 정확한 원문으로 이동했고, 두 크기에서 가로 넘침은 없었다. 새로고침 후에도 구분 표시가 복원됐다.
- 화면과 서버 응답의 두 승인 필드가 원본과 일치했다. 자동 검사 Python 115개와 JavaScript 20개가 통과했다.
- 최종 실행의 제공자 지표는 SAM 2.443초, Muse 21.499초였다. 한 번의 실행에서 관찰한 값이며 브라우저 전체 시간이나 개선 효과를 뜻하지 않는다. 검증은 기존 연출 사진의 금지 사례 한 건과 자동 회귀 검사 범위다.

3분 [시연 대본](DEMO_RUNBOOK.md)은 파란 보관표의 잘못된 규칙 적용 요청부터 시작한다. 금지 이유와 노란 표의 조건을 보여준 뒤 접수대 사례의 작성·승인 흐름으로 전환한다. [제출 소개 초안](SUBMISSION_PACKET.md)도 같은 사례를 설명한다. 수정 전후 화면과 관찰값은 `state/evidence/portfolio-verdict-clarity/`에 보관했다.

## 2026년 11월 3일 · Docker에서 노란 대여표의 허용과 판단 유보 확인

후보 커밋 `dc44259`의 파일을 `git archive`로 추출해 저장소의 Dockerfile로 Linux ARM64 이미지를 빌드했다. 새 Docker 볼륨을 `/data`에 연결한 일회용 컨테이너에서 패키지의 `seed_demo(..., scenario="storage-tags")`를 실행했다. 서비스는 같은 볼륨과 기존 `scripts/serve_hosted.py`로 시작했다. 이미 준비한 시나리오를 열기 위해 `SHOWME_SEED_DEMO=0`을 지정했고, 로컬 브라우저에서 확인하도록 `127.0.0.1`에만 포트를 연결했다. 모델 키는 서비스 컨테이너 시작 시 전달했다.

- `/api/health`, `/demo`, 승인 사진이 HTTP 200으로 열렸다. 데모는 승인본 1개·1단계였으며 JPEG의 SHA-256과 두 승인 문구는 앞선 새 복제본 검증과 같았다. 컨테이너의 Python은 3.12.15였고 의존성 검사도 통과했다.

## 2026년 11월 3일 · 판정 제목과 금지 근거 라벨의 일치

앞선 Docker 검증에서 모델은 노란 대여표의 발급 요건이 빠진 질문에 `conditional`을 반환했다. 그러나 용도 문장에 금지 이유를 뜻하는 `basis`를 붙였고, 화면은 이를 ‘진행 불가 근거’로 그대로 표시했다.

**결정.** 금지 근거 표시는 화면이 받은 최종 판정이 `blocked`일 때만 사용한다. 허용·유보 답변에 들어온 `basis` 인용은 원문 안에서 일반 기준으로 표시한다. 이미 저장한 답변에도 같은 표시 규칙을 적용할 수 있도록 화면의 인용 표현을 만드는 지점에서 처리했다. 판정과 조건의 충족 상태, 승인 원문은 응답 그대로 사용한다.

| 같은 유보 응답 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 제목 | 조건을 더 확인해야 해요 | 조건을 더 확인해야 해요 |
| 노란 표의 용도 문장 | 진행 불가 근거 | 판정에 사용한 승인 기준 |
| 교육 이수 또는 책임자 동행 | 추가 확인이 필요한 기준 | 추가 확인이 필요한 기준 |
